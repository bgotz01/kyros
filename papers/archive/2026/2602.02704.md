###### Abstract

Reasoning over ultra-long documents requires synthesizing sparse evidence scattered across distant segments under strict memory constraints.
While streaming agents enable scalable processing, their passive memory update strategy often fails to preserve low-salience bridging evidence required for multi-hop reasoning.
We propose InfMem, a control-centric agent that instantiates System-2-style control via a PreThink–Retrieve–Write protocol.
InfMem actively monitors evidence sufficiency, performs targeted in-document retrieval, and applies evidence-aware joint compression to update a bounded memory.
To ensure reliable control, we introduce a practical SFT RL training recipe that aligns retrieval, writing, and stopping decisions with end-task correctness.
On ultra-long QA benchmarks from 32k to 1M tokens, InfMem consistently outperforms MemAgent across backbones.
Specifically, InfMem improves average absolute accuracy by +10.17, +11.84, and +8.23 points on Qwen3-1.7B, Qwen3-4B, and Qwen2.5-7B, respectively, while reducing inference time by 3.9 on average (up to 5.1 ) via adaptive early stopping.

## 1 Introduction

Large Language models (LLMs) have achieved remarkable performance across a wide range of tasks  (Achiam et al., 2023; Touvron et al., 2023; DeepSeek-AI, 2025). Despite these successes, they continue to exhibit limitations on tasks that require long-context abilities. In particular, long-document question answering increasingly demands inference over extreme-length inputs— ranging from multi-hundred-page legal contracts to codebases spanning hundreds of thousands of tokens—where correct answers hinge on a few sparse, widely scattered facts rather than the global gist (Shaham et al., 2022; An et al., 2024).
Existing long‑context LLM research largely focuses on improving the generic ability of models to operate over long inputs—either by (i) increasing the amount of text that can be ingested through architectural innovations (Liu et al., 2023; Gu & Dao, 2024; Yang et al., 2024b) or (ii) encouraging models to generalize beyond their pre‑training context window (Press et al., 2021; Su et al., 2024; Peng et al., 2024a). and reduce length‑extrapolation failures. While these methods mitigate the computation burden or preserve the basic language ability of LLM on extended inputs, the foundational LLMs still face challenges to make use of the relevant information in the extremely long contexts, as recent works show significant degradation when models must access correct information in the middle of long inputs (Liu et al., 2024b; Salvatore et al., 2025).

Instead of feeding an entire ultra‑long document into an LLM directly, a practical alternative is streaming processing: the document is segmented into chunks read sequentially, and the model maintains a fixed‑size bounded memory that is selectively overwritten at each step, yielding constant memory cost and linear‑time computation (Packer et al., 2023; Yu et al., 2025). While these methods improve efficiency, they introduce an unidiretional optimization bias. Specifically, every chunk is forced through the same fixed‑size memory bottleneck, regardless of the complexity of the underlying question. This uniform treatment implicitly assumes that all segments of the document contribute equally to the final answer. However, long‑document QA naturally contains a mixture of high‑complexity and low‑complexity queries. Some questions require multi‑step reasoning over subtle cross‑section dependencies, while others only demand direct retrieval of a single explicit fact. This mismatch creates a structural dilemma: to preserve information for complex questions, the memory must retain rich, high‑fidelity representations of earlier content; yet to remain within the fixed memory budget, the system must heavily compress each chunk, inevitably discarding fine‑grained details.

This structural dilemma exposes a deeper limitation of streaming-based
long-context processing: the system cannot adapt its reasoning depth or memory
preservation to the complexity of the question. Complex queries demand
multi-step abstraction and the retention of subtle cross-section dependencies,
yet a fixed-size memory with uniform compression treats all incoming
information homogeneously. In the language of dual-process theory
(Kahneman, 2011), such architectures are locked into fast,
reflexive ”System-1” heuristics where deliberate, state-dependent System-2
control is needed. While recent work on test-time scaling
(Wei et al., 2022; Jaech et al., 2024; DeepSeek-AI, 2025) shows that LLMs
can dynamically allocate computation at inference time, no existing streaming
framework channels this capacity into principled memory control for
long-context QA.

We address this gap with InfMem, a bounded-memory agent that replaces passive
compression with an explicit, System-2-style control loop
(Kahneman, 2011; Sumers et al., 2023), instantiated as a
PreThink–Retrieve–Write protocol. At each streaming step,
PreThink assesses whether the accumulated evidence suffices for the
query; if not, Retrieve issues targeted queries against a global
document index, and Write jointly compresses the retrieved passages,
the current chunk, and the existing memory within a fixed budget. Once evidence
is deemed sufficient, the loop stops early, protecting consolidated memory from
redundant overwrites and curtailing computation. To make these control
decisions reliable rather than heuristic, we combine supervised fine-tuning on
reasoning-correct trajectories with reinforcement learning that aligns
retrieval, writing, and stopping with end-task correctness and efficiency.
On ultra-long QA benchmarks (up to 1M tokens), InfMem outperforms the state of the art by over 10 points across three Qwen-series backbones while reducing inference latency by 3.9 on average via adaptive early stopping.

## 2 Related Work

##### Long-Context Modeling and Efficiency.

Frontier models now scale to million-token regimes (Qwen Team, 2025; Wan et al., 2025b; Yang et al., 2025b; Wan et al., 2025a), and efficient architectures such as linear attention and SSMs reduce the quadratic cost of self-attention (Gu & Dao, 2024; Yang et al., 2024b). However, both transformers and their efficient alternatives consistently suffer from length generalization issues when trained on short sequences and tested on long ones, requiring careful intervention either before or after training (Press et al., 2022; Peng et al., 2024b; Lu et al., 2025). Limited capacity is a general challenge when processing long contexts for architectures with recurrent states or local windows, and incorporating additional modules to augment this capacity can improve performance on retrieval-heavy tasks (Wang et al., 2025b; Ma et al., 2026). Yet expanded capacity alone does not ensure effective reasoning: retrieval-heavy tasks still exhibit ”lost-in-the-middle” degradation (Liu et al., 2024a; Weston & Sukhbaatar, 2023), and monolithic processing offers no explicit control over which evidence is retained or discarded. Integrating retrieval natively into the reasoning chain improves context fidelity (Wang et al., 2025a), but presumes the document fits within the context window and offers no mechanism for streaming consolidation under a memory budget.

##### Bounded-Memory Agents.

Zhang et al. (2023) formulate LLMs as semi-parametric RL agents that learn to retrieve and update memory.
MEM1 (Zhou et al., 2025), Memory-R1 (Yan et al., 2025), and MemGPT (Packer et al., 2023) introduce dedicated memory mechanisms but primarily target conversational settings (Maharana et al., 2024), prioritizing state tracking or persona consistency rather than evidence aggregation over a single document.
Beyond textual memory, context can also be consolidated parametrically—by transforming it into weight updates (Cao et al., 2025) or via lifelong model editing (Wang et al., 2026)—which faces an analogous plasticity–stability dilemma between absorbing new evidence and preserving consolidated knowledge.
For long-document QA, MemAgent (Yu et al., 2025) is the most directly relevant: it streams chunks sequentially and recurrently compresses each chunk with the existing memory. However, this fixed routine cannot assess memory sufficiency, revisit lost context, or terminate early.

## 4 Training InfMem

The PreThink–Retrieve–Write protocol poses training challenges absent in standard language modeling: the model must produce heterogeneous outputs (retrieval decisions, free-form queries, and compressed memory) whose quality is only revealed at the end of a long rollout, with no ground-truth labels for intermediate decisions. This motivates a two-stage recipe. Stage 1 (SFT) teaches the model to produce protocol-valid outputs—well-formed function calls, schema-consistent memory updates, and formatted answers. Stage 2 (RL) then optimizes the control policy—when to stop, what to retrieve, and how to compress—via outcome-based rewards propagated through the full trajectory.

### 4.1 SFT Warmup via Supervised Distillation

We distill a strong teacher (Qwen3-32B) into a smaller student using trajectories from the PreThink–Retrieve–Write loop. For each question, the teacher executes the full protocol, optionally guided by golden question decompositions (e.g., for MuSiQue) to elicit cleaner retrieval traces, in the spirit of evidence-grounded trajectory synthesis (Li et al., 2026). Crucially, these hints are given only to the teacher; the student never observes decompositions, gold document IDs, or any teacher-side annotations. The subsequent RL stage operates entirely without such hints yet yields substantial additional gains (Table 6), confirming that the learned control policy—not teacher supervision—drives the final performance.

### 4.2 RL Alignment with Reward Design

While SFT ensures protocol-compliant execution, it does not optimize the control policy itself—when to stop, what to retrieve, and how to compress under the overwrite budget.
We apply RL to align these decisions with end-task success and efficiency.

### 5.1 Experimental Setup

##### Datasets and backbones.

We utilize four datasets spanning a spectrum of reasoning demands: SQuAD (Rajpurkar et al., 2016), HotpotQA (Yang et al., 2018), 2WikiMultiHopQA (Ho et al., 2020), and MuSiQue (Trivedi et al., 2022).

### 5.2 Results on Various Input Lengths up to 1M Tokens

Table 1 reports results on synthesized long-context QA benchmarks evaluated across Qwen3-4B and Qwen2.5-7B. We compare our methods against standard long-context baselines (YaRN, RAG) and strong iterative or memory-construction frameworks like RESP and Mem- (see Appendix B for full reproduction details). Two further retrieval-based baselines evaluated under a matched in-document corpus—Search-R1 (Jin et al., 2025), an RL-trained retrieval-decision policy, and Self-RAG (Asai et al., 2024), in both a prompted train-free variant and a checkpoint we train ourselves—are reported in Appendix F.2; InfMem outperforms both even when they use substantially larger backbones.

Models equipped with the length generalization method (YaRN (Peng et al., 2024a)) or conventional retrieval mechanism (RAG (Lewis et al., 2020)) degrade sharply beyond 128k tokens, often collapsing to single digits at 1M. iterative RAG system (RESP (Jiang et al., 2025)) and recent bounded memory agent method (Mem-  (Wang et al., 2025c)) mitigate this decline but still underperform both MemAgent and InfMem on average. InfMem consistently achieves the strongest results across all settings.

This performance advantage becomes particularly pronounced on complex multi-hop reasoning tasks where evidence is scattered. For instance, on the MuSiQue benchmark at 1M tokens (using Qwen3-4B+RL), InfMem achieves a score of 56.86 compared to MemAgent (Yu et al., 2025)’s 35.91. Similarly, on 2WikiMultiHopQA at 1M tokens, InfMem reaches 66.39 versus 35.18. On single-hop tasks like SQuAD, the performance gap narrows slightly, as MemAgent’s fixed, reactive compression is generally sufficient for direct fact extraction. However, for multi-hop queries, MemAgent’s recurrent architecture is highly susceptible to gradual information loss over extended horizons. In contrast, InfMem leverages explicit reasoning and decision-making capabilities to dynamically decompose complex questions into manageable sub-problems. Finally, the proposed SFT RL training recipe further amplifies these structural advantages by optimizing the agent’s sequential decision-making and adaptive stopping policies. Consequently, RL-InfMem establishes a decisive lead, outperforming RL-MemAgent by an average margin of over 10 points across both evaluated backbones.

## 7 Conclusion

In this work, we present InfMem, a cognitive agent designed to resolve the fidelity dilemma in ultra-long context reasoning. By integrating structured evidence management with a robust SFT RL training pipeline, InfMem excels in long-horizon search and retrieval. Empirical evaluations on 1M-token benchmarks demonstrate that InfMem outperforms the state-of-the-art MemAgent with double-digit accuracy improvements across various Qwen models, while simultaneously reducing latency by 3.9 via inference early stopping. Our findings suggest that as context windows scale, the primary bottleneck shifts from raw memory capacity to cognitive control: the ability to effectively discern and ”know what is known”.

## Ethics Statement

This work proposes a method for improving long-document question answering under bounded compute and memory budgets.
The approach does not introduce new datasets, collect personal data, or target high-risk application domains.
Potential benefits include improved efficiency and reliability in document analysis tasks such as technical review and knowledge synthesis. In this work, LLMs were used solely for grammar checking and textual correcting, consistent with accepted usage guidelines.

## Appendix A Implementation

### A.1 Prompts and Templates

We use two structured templates to implement the recurrent Retrieve–Compress loop:
a Retriever Template for decision making and query formation, and a Memory Template for faithful evidence compression.

##### Retriever Template (Figure 3)

The retriever prompt conditions on the current question and the accumulated memory, and asks the model to (i) assess whether the memory already contains sufficient evidence to answer, and (ii) if not, produce a function-call specification for external retrieval.
Concretely, the template outputs a discrete decision (STOP vs. RETRIEVE); when retrieval is needed, it emits a search query and a top_k value.
This design turns retrieval into an explicit, controllable action: the model is encouraged to issue broad queries when evidence is missing, refine queries when retrieval results are noisy or mismatched, and allocate top_k based on uncertainty (larger when multiple candidate entities/facts exist; smaller when the target is specific).
By tying retrieval decisions to the evolving memory state, the agent can avoid redundant searches and terminate early once decisive evidence has been accumulated.

##### Memory Template (Figure 4)

The memory prompt performs bounded, evidence-centric compression .
At each step, it is given two sources: (1) the newly retrieved chunk (high-relevance but potentially noisy) and (2) a recurrent chunk from the running context (stable but may be redundant).
The template instructs the model to extract only answer-relevant facts, normalize entities/aliases, and write a compact memory update that preserves verifiable evidence (names, dates, titles, and relations) while discarding stylistic or speculative content.
Importantly, the template enforces selective compression across the two inputs: it prioritizes new complementary evidence from retrieval, but retains previously stored facts when they remain useful, preventing memory drift and uncontrolled growth.

### A.2 Data Construction Details

##### Unified long-context synthesis pipeline.

All synthesized long-context QA instances share the same supervision format: a question and an answer , together with a set of gold evidence documents (or paragraphs) annotated by the source dataset.
We convert each original instance into a single long document by mixing (i) the gold evidence documents, and (ii) a large pool of distractor documents sampled from the same corpus.
Concretely, for each instance we build three text pools: the query ( ), the evidence set ( ), and a distractor pool ( ) drawn from the dataset’s training corpus.11
1

We sample distractors from the same corpus to preserve domain/style match, making the task harder than using out-of-domain noise.
We then create a candidate document list by shuffling documents with a fixed random seed, insert each gold document exactly once at the document level, and keep appending distractors until reaching a target token budget.
This yields a controlled setting where (1) the answer is always supported by , while (2) retrieval difficulty scales with the number of distractors and total context length.

#### A.2.1 Cold-start SFT data

Following the NIAH-style long-context QA construction in MemAgent, we synthesize cold-start SFT data from three QA sources: HotpotQA, SQuAD, and MuSiQue.
Each source contributes 4,096 instances sampled from its training split.
For each instance, we construct a long document at a fixed target length (32K tokens) by iteratively inserting distractor documents until the budget is met.22
2

In practice, we first pre-scan candidate distractor documents to determine how many whole documents can be inserted under a given token budget.
We then construct the long document in a single pass by inserting all gold evidence documents once and appending the maximal number of distractors without exceeding the target length, truncating only at document boundaries.

We use Qwen3-32B as the teacher with thinking enabled to generate protocol-consistent interaction traces under our PreThink–Retrieve–Write workflow:
the teacher (i) plans and emits structured retrieve calls, (ii) updates a bounded agent memory by writing compressed evidence, and (iii) decides when to stop retrieving and answer.
We then distill student backbones (Qwen3-1.7B, Qwen3-4B, and Qwen2.5-7B-Instruct) on these trajectories.

##### Question decompositions.

MuSiQue provides an optional question decomposition (multi-hop sub-questions).
We feed decompositions only to the teacher to elicit cleaner and more stable planning traces; students never observe decompositions, gold document IDs, or any teacher-side annotations during either training or inference.
For HotpotQA and SQuAD, the teacher autonomously decides whether to decompose the question in its private reasoning and how to formulate retrieval queries.

##### Trajectory filtering.

To ensure supervision quality, we retain only traces whose final answers are correct under the official evaluation protocol of the underlying dataset and discard all failed attempts. We additionally remove excessively long traces that would exceed the memory budget or truncate the agent memory/state; this ensures the student is trained on trajectories that are feasible at inference time under the same bounded-memory constraints.

After this filtering process, we decompose the successful trajectories into individual turns, resulting in a total of 29,717 single-turn dialogue instances. These instances constitute our final SFT dataset for training the student backbones.

#### A.2.2 RL training data.

For RL training, we utilize the same synthesis pipeline to extend the context length of HotpotQA instances to approximately 28K tokens. We retain the original question-answer pairs while scaling the retrieval difficulty through the insertion of distractors. During the reinforcement learning phase, the model is optimized using the Exact Match (EM) score between the generated response and the ground-truth answer as the primary reward signal. This setup ensures that the environment remains consistent with our SFT stage, allowing the RL process to focus specifically on refining the agent’s decision-making—such as retrieval timing and memory management—under long-context constraints.

#### A.2.3 Evaluation Benchmark

##### Synthesized long-context QA benchmarks (extreme scaling).

To evaluate robustness under extreme context scaling, we create long-document variants following the NIAH-style construction for representative multi-hop QA tasks, including HotpotQA, 2WikiMultihopQA, and MuSiQue; we also include the synthetic SQuAD setting used in MemAgent for direct comparison.
We use each dataset’s test split and sample 128 instances per task.
For each fixed question set, we generate multiple test variants at increasing target lengths (e.g., 32K/28K, 64K/56K, 128K/112K, up to 1M/896K tokens) by progressively inserting more distractors while keeping the gold evidence set unchanged.
Gold evidence is inserted once per instance at the document level with a fixed seed, and distractors are sampled from the same corpus to preserve distributional match.
This protocol ensures that differences across lengths reflect only the effect of context scaling (more distractors / longer inputs), not changes in questions or evidence.

##### Task-specific token budgets.

The minimum target length differs slightly across tasks: HotpotQA uses 28K tokens to match the document-count-based construction inherited from the RL dataset, while other tasks use fixed token budgets (32K/64K/128K/ /1M) and insert as many whole documents as allowed under each budget.

##### LongBench QA benchmarks (natural distributions).

To verify transfer beyond synthetic distractor insertions, we additionally evaluate on LongBench QA using its original documents and distributions.
We report F1 on NarrativeQA, HotpotQA, 2WikiMultihopQA, Qasper, and MuSiQue following the official LongBench evaluation protocol.

### A.3 Training setup

#### A.3.1 Model Configuration and Baselines

To ensure a rigorous evaluation, we standardize the recurrent interaction settings across both InfMem and the baseline MemAgent (based on Qwen-1.5B/4B backbones).

##### Recurrent Processing Setup.

Both models operate with a fixed recurrent chunk size of 5,000 tokens. To maintain consistency in the reasoning horizon, we align the maximum generation length (1.5k tokens) and the interaction iteration steps for both models. For InfMem, we enable BM25-based retrieval with a cap of 4,000 retrieved tokens per step. Crucially, during the memory update phase of InfMem, we explicitly filter out reasoning/thinking steps, retaining only the schema-consistent memory tokens to maximize information density.

##### Baseline Fairness.

For the MemAgent reproduction, we disable the optional “thinking mode” (as discussed in §E.1) to adhere to its standard efficient setting.It is important to note that our comparison aligns the output constraints (generation length and steps) rather than the input/memory budget. Since InfMem processes additional retrieved context (up to 4k tokens) within the same iteration framework, it is required to compress a significantly larger volume of information into the memory state compared to MemAgent.This setup ensures we are not weakening the baseline; rather, we are testing InfMem’s ability to handle higher information loads under strictly bounded generation resources.

## Appendix B Baseline Implementation Details

To ensure a fair and rigorous comparison against our proposed methods, we carefully reconstructed the experimental setups for the strong agentic baselines, RESP and Mem- . Because these methods were originally designed for different scales or exhibited generation bottlenecks, we integrated a larger Qwen3-32B backbone to maximize their competitive performance. We also standardized the configurations for our standard long-context and retrieval baselines.

RESP: We strictly follow the implementation details provided in the original paper. To accurately replicate their iterative RAG logic, we utilized their exact prompt templates. We employed Qwen3-32B as the backbone model throughout the entire process, handling the iterative reasoning, planning, summarization, and the final generation.

Mem- : We integrated the publicly available Mem- implementation directly into our evaluation framework. Specifically, we utilized their released 4B checkpoint to serve as the context manager. However, empirical observations indicated that the RL-tuned Mem- checkpoint exhibited suboptimal generative question-answering capabilities. To prevent the baseline’s performance from being unfairly bottlenecked by poor generation rather than poor context management, we decoupled the architecture: we delegated the final QA generation phase to Qwen3-32B while retaining the 4B model strictly for context management.

YaRN: For evaluations utilizing YaRN, we apply the official RoPE scaling configurations established for the Qwen2.5 and Qwen3 models. Specifically, we set the rope_type to yarn, apply a scaling factor of 4.0, and maintain the original_max_position_embeddings at 32,768.

RAG: For the standard RAG baseline, our reported main results utilize a chunk size of 1,000 tokens and retrieve the top-6 chunks. To determine this optimal configuration, we conducted an ablation study on the synthesized HQA benchmark across context lengths of 28k, 56k, and 112k using Qwen3-4B. We evaluated multiple retrieval variants, including top-12 with 1,000-token chunks, top-6 with 2,000-token chunks, top-2 with 1,000-token chunks, and top-6 with 1,000-token chunks. Empirical results demonstrated that retrieving the top-6 chunks with a 1,000-token chunk size consistently yielded slightly better performance, and it was thus selected as the default configuration for all RAG evaluations.

### C.1 sft enhance dieversity

##### Why SFT warmup is necessary.

SFT is critical for making tool-use reliable in our agentic retrieval loop.
In practice, base backbones do not consistently exhibit disciplined query planning: the smaller Qwen3-1.7B has limited intrinsic reasoning capacity, while the instruction-tuned Qwen2.5-7B still fails to reliably trigger deliberate multi-step planning under our Retrieve–Compress protocol.
Empirically, Table 5 and Table 6 shows consistent improvements from Train-free to SFT across both LB and RULER-QA, and even the strongest backbone (Qwen3-4B) benefits substantially, suggesting that supervised warmup improves not only downstream QA accuracy but also the quality of intermediate actions.

Qualitatively, Figure 5 visualizes retrieval trajectories on the same instance: without PRETHINK, the model often degenerates into copying the question (or a lightly rewritten variant) as the search query, leading to repetitive, low-information retrievals.
After SFT, the planner conditions on retrieval history and the current memory state, identifies missing links needed for multi-hop composition, and issues targeted follow-up queries, yielding more informative function calls and more dependable evidence aggregation.

### C.2 RL boost the performance

RL further strengthens InfMem beyond SFT by explicitly optimizing long-horizon tool-use under verifiable QA rewards, yielding gains along two complementary axes:
(i) memory compression / evidence writing, and (ii) planning / retrieval control.

As shown in Figure 6, the pre-RL agent may follow a superficially similar retrieval pattern, yet fails at the decisive step of extracting and committing the key sentence into memory: rather than grounding “Niou’s seat” in the exact district that links to the previous holder, it writes an unrelated political chain and hallucinates an incorrect former lawyer.
After RL, the agent consistently identifies the decisive evidence chain (Niou NY Assembly 65th district Sheldon Silver) and writes a compact, answer-ready memory, enabling a correct final answer.

Figure 7 highlights a complementary improvement in planning: RL teaches the agent to regulate exploration by adapting retrieval scope (e.g., via top- control) instead of drifting or stopping prematurely.
Before RL, the agent prematurely concludes that no tactical RPG franchise exists beyond the “Wars” series; after RL, it expands search when uncertain, discovers Fire Emblem, and composes the correct numerical answer from explicit evidence.

Taken together, these case studies suggest that RL does not merely increase tool usage; it trains the agent to write the right information into memory and to plan the right next action—balancing targeted exploration with timely stopping.

### C.3 Early stop

Beyond accuracy, early stopping substantially improves inference efficiency. As shown in Fig. 8, once PreThink determines that the required evidence is already present in memory, the agent explicitly terminates the recurrent retrieve–write loop. This allows the model to exit inference as soon as it is confident in the answer, rather than continuing unnecessary iterations over the remaining context. As a result, inference time is no longer proportional to the document length or number of chunks (i.e., avoiding the typical recurrent generation cost), and instead approaches constant-time behavior in practice when decisive evidence is found early.

## Appendix E Ablation and Analysis of Thinking Dynamics

### E.1 Rationale for Defaulting to No-Thinking in Baseline

When reproducing MemAgent-RL on the Qwen3-series, we adopt the no-thinking setting as the default configuration. This choice is primarily driven by alignment with the original pipeline, as the official MemAgent-RL setup (based on Qwen2.5-Instruct) does not inherently support thinking mode. However, beyond consistency, we empirically validate that enabling thinking in the baseline architecture is often counterproductive.

MemAgent (NoThink-RL) Process: 
From Document 81, it is stated that Toronto FC is a team in the Major League Soccer Eastern Conference. However, this information is not directly applicable to Nick Garcia.
From Document 17, it is stated that the Columbus Crew is a team in the Major League Soccer Eastern Conference. However, this information is not directly applicable to Nick Garcia. 
From Document 10, it is stated that Occhiuto played for the Buffalo Stallions …
From Document 17, it is stated that the Columbus Crew is a team in the Major League Soccer Eastern Conference. [Repetition] 
From Document 10, it is stated that Occhiuto played for the Buffalo Stallions of the Major Indoor Soccer League. However, this information is not relevant to the problem. 
…(Repeats ”Columbus Crew” and ”Buffalo Stallions” which affect information density)

InfMem (Ours) Process: 
<think>

</think> 

The retrieved chunk (Document 109) explicitly states that Nick Garcia played for Toronto FC. Additionally, the memory section confirms that Toronto FC is an MLS team in the Eastern Conference (Document 81). 

Updated Memory: 
- Nick Garcia played for Toronto FC in MLS.

Final Answer: Nick Garcia played soccer for Toronto FC in the Eastern Conference.

Figure 11: Qualitative Comparison of Memory Purity. Left: MemAgent (NoThink) is susceptible to recurrent noise, tending to process and accumulate irrelevant information (e.g., details about unrelated teams like Columbus Crew) which dilutes memory utility. Right: In contrast, InfMem utilizes the reasoning mechanism to actively filter out these distractors. By synthesizing only the critical evidence, InfMem maintains a memory of significantly higher quality and purity, ensuring that only high-fidelity facts relevant to the query are preserved.

The baseline MemAgent relies on a lightweight controller for naive compression, deciding strictly whether to write or skip the current chunk. In this regime, enabling thinking mode triggers an “over-deliberation” behavior. As illustrated in the case study (Figure 10), the agent expends substantial reasoning on loosely related chunks, which blurs the write/skip boundary.

Quantitative Evidence of Instability. This destabilization is quantitatively captured in Table 8. While enabling thinking in the baseline (MemAgent Think-RL) significantly improves the model’s ability to discover answers (Found: 76.04% vs. 72.46%), it introduces severe volatility. The active reasoning process makes the memory vulnerable to recurrent noise, causing the Preserved rate to drop sharply from 69.53% to 65.43%. This confirms that in the baseline architecture, the benefits of enhanced extraction are negated by the instability of memory updates, justifying our choice of the no-thinking configuration for controlled comparisons.

### E.2 Decoupling Reasoning from Instability: The InfMem Advantage

Crucially, the analysis above raises a fundamental question: Is reasoning inherently detrimental to memory retention in recurrent systems? Our results with InfMem suggest the answer is no. The instability observed in the baseline stems not from the thinking process itself, but from the naive compression mechanism that fails to filter the generated reasoning paths.

Stability via Dynamic Chunking.
As shown in Table 8, InfMem effectively mitigates the extraction-retention trade-off. Despite leveraging reasoning to enhance information processing, InfMem maintains a robust retention profile. Its average Preserved rate (69.77%) is not only significantly higher than the unstable MemAgent Think-RL but is fully comparable to the conservative MemAgent NoThink-RL baseline (69.53%). This indicates that InfMem’s Dynamic Chunking successfully concentrates deliberation on salient regions, allowing the model to benefit from deep reasoning without succumbing to the forgetting issues typical of recurrent updates.

Memory Purity and Downstream Performance.
The advantages of InfMem extend beyond mere retention statistics to the quality of the preserved information (Fig 11). A key observation from Table 8 is the performance discrepancy: while InfMem and MemAgent NoThink-RL preserve a similar number of answers ( 69%), InfMem achieves substantially higher downstream performance (64.85% vs. 56.94%).

### F.1 Generality Across Model Families

All backbones in the main results belong to the Qwen family.
To test whether the control loop is tied to that family, we run the identical InfMem inference protocol on Gemma-4-E4B-IT, an instruction-tuned model of comparable effective size from a different training pipeline, without any SFT or RL on that backbone, and compare it against MemAgent on the same model.
The evaluation setup follows the main comparison (HotpotQA at 112k–896k and MuSiQue at 128k–1M, 128 samples per length).

InfMem improves over MemAgent on all eight (task length) configurations, by to F1 (Table 12), and reproduces the two qualitative patterns of the Qwen results: the gain is larger on multi-hop than on single-hop questions, and it grows with context length.
Most directly relevant to the question of attribution, the average marginal lift on multi-hop MuSiQue is essentially the same on the two families ( on Gemma vs. on Qwen3-4B), indicating that the benefit of the control loop is a property of the protocol rather than an artifact of Qwen-specific training.
On single-hop HotpotQA the lift is somewhat larger on Gemma ( vs. ), as the RL-trained Qwen baseline is already stronger on this task and leaves less headroom.
The efficiency profile transfers as well, with up to lower per-sample latency at 896k (Table 13).
We note that InfMem on the zero-shot Gemma backbone still trails InfMem on the RL-trained Qwen3-4B by roughly – F1 in absolute terms.

##### Model-family dispatch.

Supporting a non-Qwen backbone requires no change to the control loop, only to prompt rendering and response parsing.
We add a tokenizer-based dispatch layer that detects the backbone family and selects the corresponding format: Qwen models use the native function-call markers, whereas Gemma uses the standard chat template with tool declarations and the model’s tool-call and thinking delimiters.
Because those delimiters are special tokens, decoding for the Gemma path must preserve special tokens; the Qwen path is unchanged.

### F.2 Additional Retrieval-based Baselines

Table 14 compares InfMem against two further families of retrieval-based systems under a matched in-document corpus.

##### Search-R1.

Search-R1 is an RL-trained retrieval-decision policy, and is therefore the closest learned-control baseline to InfMem.
We use the officially released qwen2.5-7b-em-ppo checkpoint and keep its trained <think>/<search>/<information>/<answer> loop intact, replacing only its open-domain Wikipedia/dense retriever with the same in-document BM25 index used by InfMem and MemAgent, so that the comparison isolates the quality of the search policy rather than the retrieval corpus.
Search-R1 never places the long document in its context: it emits a query and receives the top-3 in-document chunks as <information>, so its effective context stays small and its scores are nearly flat across lengths.
At the same backbone scale, it trails InfMem by F1 on HotpotQA and F1 on MuSiQue (averaged over the four lengths), and it is also below our 4B InfMem ( vs. ).
It does clearly beat the no-control MemAgent baseline on multi-hop questions ( vs. ), confirming that a learned retrieval decision helps; the InfMem loop helps more.

##### Self-RAG.

We evaluate Self-RAG in two forms.
The first, denoted prompted Self-RAG-style RAG, is a train-free pipeline on Qwen3.6-35B-A3B (thinking mode) that uses the same in-document BM25 retriever as our other baselines, prompts the model to emit Self-RAG-style reflection signals (retrieval, relevance, support and utility), and ranks candidate answers with the weighted arg-max rule of the original paper.
Despite a much larger backbone, it stays – F1 below our 4B InfMem at every length on HotpotQA, and the gap widens sharply on multi-hop MuSiQue ( F1 from 128k to 1M).

That collapse is localized to retrieval rather than to generation.
The fraction of questions whose retrieved passages actually contain the gold answer drops from on HotpotQA to on MuSiQue, whereas the fraction whose reasoning trace mentions the answer barely moves ( to ); consequently the model abstains outright (“not provided in the given documents”) on – of MuSiQue questions.
Across both tasks the F1 of this baseline tracks its retrieval hit rate almost exactly ( F1 at hit rate on HotpotQA, F1 at on MuSiQue), i.e. a single question-shaped BM25 query essentially decides the outcome.
This is precisely the failure mode that query reformulation prevents: Search-R1 is also retrieval-only and likewise never sees the full document, but because it re-issues queries across turns it loses only relative when moving from HotpotQA to MuSiQue, against for this Self-RAG-style pipeline.

The second is a Self-RAG generator we trained ourselves on Qwen3-4B-Instruct, following the official recipe (Alpaca-format prompts, the 15 reflection tokens with mean-initialized embeddings, paragraph-content loss masking, and the 150K official Self-RAG training instances), in order to rule out the possibility that the official checkpoints underperform only because they are built on older Llama-2 backbones.
On Self-RAG’s in-domain single-hop setting, PopQA, evaluated with the official short-form script, our checkpoint reaches accuracy and exceeds the official selfrag_llama2_7b checkpoint ( ), confirming that it is correctly trained and competitive in the domain Self-RAG targets.

On our long-context benchmark, however, all Self-RAG variants remain far below InfMem (Table 15); we report sub-EM here because Self-RAG variants often emit reflection-token-style outputs rather than the short answers expected by our evaluator.
We evaluated the official checkpoints under both inference algorithms of the original paper, short-form (single-step per-passage reranking) and long-form (multi-step beam search), and verified that they emit valid reflection tokens, so the gap is not a formatting artifact.
The explanation is a task–paradigm mismatch rather than model capacity or checkpoint staleness: Self-RAG’s retrieve-then-critique paradigm assumes that a single retrieved passage is largely sufficient to answer, whereas our setting requires synthesis across passages.
The short-form algorithm only ranks answers produced from individual passages, and the long-form algorithm performs no query reformulation, so it typically fails to retrieve second-hop evidence and effectively collapses to single-passage answering.

### F.3 Token, Latency and Storage Accounting

##### Decode tokens and latency across lengths.

Table 17 reports per-sample decode tokens together with per-sample latency for InfMem and MemAgent across six context lengths.
Below 56k, the fixed PreThink overhead makes InfMem slightly more expensive in tokens, while its latency is already on par.
From 112k onward InfMem dominates on both axes, saving – of the tokens and – of the wall-clock time.

As shown in Table 16, while the total number of chunks averages 202.8, InfMem 1-stop processes only 20.5 chunks on average (approximately 10% of the full context), and InfMem 3-stop requires just 32.6 steps (16%). This demonstrates that our adaptive stopping policy effectively identifies when sufficient information has been gathered, avoiding unnecessary computation over the remaining context.

Latency is saved faster than tokens (at 896k, the wall-clock but the tokens): MemAgent’s cost grows with the number of chunks it must stream, whereas InfMem keeps a constant-size working memory and issues only a few retrieval rounds, so its wall-clock grows about from 28k to 896k against about for MemAgent.

##### Retrieval and memory budget.

Building and querying the index is a negligible fraction of the total cost (Table 11): InfMem issues about four retrieval calls per sample on average, and the BM25 build and lookup together account for well under of per-sample latency even at 896k.
The working memory is bounded by construction, at a 5k-token recurrent chunk plus a 1k-token memory slot per step, and is therefore constant in the input length.
