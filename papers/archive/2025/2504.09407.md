###### Abstract.

Usability testing is a fundamental research method that user experience (UX) researchers use to evaluate and iterate their new designs. But what about evaluating and iterating the usability testing study design itself?
Recent advances in Large Language Model-simulated Agent (LLM Agent) research inspired us to design UXAgent to support UX researchers in evaluating and iterating their study design before they conduct the real human-subject study.
Our system features a Persona Generator module, an LLM Agent module, and a Universal Browser Connector module to automatically generate thousands of simulated users and to interactively test the target website.
The system also provides a Result Viewer Interface so that the UX researchers can easily review and analyze the generated qualitative (e.g., agents’ post-study surveys) and quantitative data (e.g., agents’ interaction logs), or even interview agents directly.
Through a heuristic evaluation with 16 UX researchers, participants praised the innovation of our system but also expressed concerns about the future of LLM Agent usage in UX studies.

## 1. Introduction

Usability testing is a fundamental research method for evaluating the user experience (UX) of a new feature or a new webpage design (Shaw, 1996).
Typically, a UX researcher (or a UI/UX designer, product manager, etc.) leads the design and execution of a usability testing study: they start with a new feature or web design, and then they need to come up with a UX study design (e.g., A/B testing and the user tasks), recruit participants, execute the study, monitor, and analyze the data.
However, the current process of conducting usability testing often faces challenges, especially in the study design stage and the study execution stage (Følstad et al., 2012; Hertzum and Jacobsen, 2003; Kuang et al., 2022; Nørgaard and Hornbæk, 2006).
In the study design stage, researchers often focus on collecting early feedback on new feature design to iterate the feature, but the study design itself is left unevaluated (Shaw, 1996).
Study design flaws that surface only during execution can lead to costly consequences. This is especially critical when working with underrepresented groups (e.g., non-binary shoppers), where participants are a limited and valuable resource, thus the findings may not be significant or insightful.
In such cases, a UX practitioner in a company may not even have a second chance to iterate the study design.

To alleviate this issue, researchers have practiced using pilot study sessions (Decker-Maurer, 2012) or empathy-based research methods (Särkelä and Suoranta, 2020):
Researchers often conduct a limited number of pilot study sessions before the actual study execution to test validity and uncover design flaws. However, these sessions are time-consuming and financially costly, since their data are not considered valid test data and require additional participant recruitment (Decker-Maurer, 2012).
Researchers sometimes also apply an empathy-based research method, during which they attempt to put themselves in the shoes of their target users, especially when designing and studying for an underrepresented user population (Särkelä and Suoranta, 2020).
However, this method is inherently limited, as researchers may fail to accurately represent the target population and may unintentionally introduce bias (Wharton et al., 1992).
These limitations highlight the need for novel methods and systems that can offer early feedback on the study design as well as on the feature designs to support UX researchers.

With the advancement of Large-Language Models (LLMs), some researchers have prompted LLMs to act as autonomous agents (i.e., LLM Agent) that can perceive the environment and generate human-like actions to interact with the environment (Wang et al., 2024).
For example, researchers have successfully empowered LLM Agents to simulate a group of 25 human agents living in a village (Park et al., 2023),
replicate participants in a social science study (Park et al., 2024; Schmidgall et al., 2024; Lee et al., [n. d.]; Gurcan, 2024), act as patients and clinicians in a hospital (Li et al., 2024b), and behave as programmers for a software development company (Qian et al., 2024).
The advances in LLM agent research inspire us that: if we can simulate diverse user behaviors and perspectives with an LLM agent as surrogates for real human-subject participants, then these surrogates can interact with real-world web environments to produce rich usability testing data.
Such data can support UX researchers to analyze and identify potential flaws in their study design before conducting real user studies, as well as offer UX researchers early feedback for feature designs.

Recently, a few LLM Agent-based systems (e.g., WebAgent (Gur et al., 2023), WebVoyager (He et al., 2024), etc.) have explored simulating human interaction behaviors with web-based systems.
For example, ReAct (Yao et al., 2023) can generate both reasoning and action trace and simulate human customers on WebShop (Yao et al., 2022), a commonly used sandbox environment for e-commerce platforms.
Another example is Computer-Using Agent systems such as OpenAI Operator11
1

https://openai.com/index/introducing-operator/ and Claude’s Computer-use API22
2

https://www.anthropic.com/news/3-5-models-and-computer-use that can complete tasks in computer environments.
However, these systems fall short of our use case: we need an LLM Agent to be able to operate with the dynamically changing web pages, to think (generate reasonings) as human users do, and to interact with the web page within a human-like responsive time interval.
The aforementioned LLM Agent systems (1) are restricted to a sandbox simulation instead of a real-world complex web system (e.g., ReAct (Yao et al., 2023)), (2) rely only on complex and heavy reasoning architectures that hinder real-time responsiveness with the web (e.g.,  (Ma et al., 2024; He et al., 2024; Gur et al., 2023)), (3) do not have the reasoning depth so the simulated behavior trace output is too simple in comparison to real-human’s actions (Sodhi et al., 2024).
These challenges call for a new LLM Agent architecture design (Fig. 2) that can balance the reasoning capabilities with interaction speed when meeting complex and diverse real-world web systems.

In this work, we propose UXAgent (Fig. 1), a system that can generate LLM Agents as usability testing participants at scale and run simulated interactions with a given real-world web environment to collect simulated user behavioral data.
The UX researcher can define a demographic distribution and use the Persona Generator to generate thousands of personas for the LLM Agents, and then use the Universal Browser Connector module to interact with webpages via Chrome.
Inspired by Park et al. (2023) and the Dual Process Theory (Kahneman, 2011; Evans and Stanovich, 2013; Zhang et al., 2025c; Christakopoulou et al., 2024), UXAgent includes an LLM Agent module with a new LLM Agent architecture to have a two-loop structure to support both in-depth reasoning and real-time response.
Our Universal Browser Connector module allows LLM Agents to seamlessly parse and interpret real-world webpages while automatically executing real actions on the webpage without the need for manually pre-defined action spaces.
UXAgent also provides a Result Viewer Interface that enables UX researchers to seamlessly review LLM agents’ interactions with web pages, examine post-study survey results, and conduct qualitative interviews with the agents.
Our position is that: LLM agents are not meant to replace human participants in UX studies, but rather to help UX researchers to iteratively revise the study design, thus to be more responsible to human participants.
LLM Agents can work together with UX researchers (human-AI collaboration (Wang et al., 2019)) in a simulated pilot study manner to provide the desired early and immediate feedback for UX researchers to further iterate their design before testing with real human participants.

To evaluate our system, we conducted a user study with 16 UX researchers and asked them to analyze usability testing data (action trace, reasoning trace, and qualitative interview) of 20 LLM Agents interacting with a shopping website, as if they were the study owners.
Our study scenario is that: a UX researcher is tasked to design a usability testing study to gather feedback for a newly designed shopping website feature (product filter menu) and propose new designs for this website feature.
Our results suggest that the UX researcher participants were able to review and analyze the LLM-agent participants’ data generated by UXAgent, identify potential study design flaws, and come up with system feature improvement ideas. In comparison to the initial UX study design, they were satisfied with their revised study designs after analyzing the data, despite some criticizing that the LLM agent’s generated actions were not what real users would do.
We conclude our paper by discussing how LLM agents may play an increasingly important role in the future of UX research.

## 2. Related Work

### 2.1. Challenges in Usability Testing

Usability testing is a core component of UX research, used to evaluate how easily users can interact with a product to achieve their goals (Shaw, 1996; Barnum, 2020; Bastien, 2010; Lewis, 2012).
It involves observing real users as they navigate through tasks and providing valuable feedback on design effectiveness (Barnum, 2020).
This method helps refine products by identifying usability issues, measuring user satisfaction, and improving overall user experience. The key benefits of usability testing include validating design choices, avoiding internal biases, and ensuring the product meets user expectations.

However, UX researchers conducting usability testing on web designs have been facing multiple challenges in the study design stage and the study execution stage (Følstad et al., 2012; Hertzum and Jacobsen, 2003; Kuang et al., 2022; Nørgaard and Hornbæk, 2006).
During the study design stage, it is often difficult for researchers to craft appropriate study protocols and gather early feedback to iteratively improve the study design.
To address this challenge, researchers have proposed guidelines and frameworks to support the design of usability testing, including methods for refining interview protocols (Castillo-Montoya, 2016; Shoozan and Mohamad, 2024; Roberts, 2020) and developing survey questionnaire items (Rasinski, 2008; Müller and Sedley, 2015; Müller et al., 2014; Koelle et al., 2020).
To further streamline this process, recent work has begun to explore automated approaches for refining study protocols. For example, Calvano et al. (2025) investigated the use of Large Language Models (LLMs) to assist in generating components of usability studies, such as user tasks and evaluation criteria.
To obtain early feedback on their designs, researchers typically rely on pilot studies, which, while valuable (Hertzog, 2008; Truong, 2017; Van Teijlingen et al., 2001; Oppenlaender et al., 2024), are time-consuming, costly, and limited in scale (Janaka et al., 2024; Oppenlaender et al., 2021).
Despite these efforts, there remains a lack of efficient and scalable methods for UX researchers to evaluate and refine study designs before conducting full-scale studies with human participants.

For the study execution stages, a key challenge lies in the high cost and effort required to recruit enough qualified participants (Nebeling et al., 2013; E et al., 2024). To mitigate these challenges, researchers have begun exploring the use of agents to simulate real human participants in usability testing (Ren and Kraut, 2014).
Prior work has introduced agents in various domains, including GUI testing (Eskonen et al., 2020), game environments (Stahlke et al., 2019; Fernandes et al., 2021), and accessibility testing (Taeb et al., 2024; Zhong et al., 2025).
A particularly notable effort is SimUser (Xiang et al., 2024), which leveraged LLM Agents to simulate usability testing for mobile applications. In their approach, a user agent simulated human interaction, while an application agent represented the mobile app. These two agents interacted during the simulation to generate behavioral data. However, because the application under test was also simulated, their approach was limited in its ability to evaluate real-world interfaces and behaviors.
Despite growing interest in agent-based usability testing, the application of agents to real-world web design usability testing remains underexplored—largely due to the complexity of real web environments and the limitations of traditional web automation technologies.

### 2.2. Simulation of Human Behavior with LLM and LLM Web Agents

In the field of HCI, recent studies have demonstrated that LLMs possess the capability to simulate human-like behaviors, enabling research on personalized agent behavior. Unlike task-oriented agents, which are typically focused on achieving narrowly defined goals, human agents or role-play agents (Chen et al., 2025) are designed with rich personas that encompass not only their roles and expertise but also their preferences, habits, and subjective viewpoints.
For example, Park et al. (2023) created a simulated town inhabited by 25 LLM Agents, each with a unique persona, and showed that these agents could exhibit believable and autonomous human-like interactions. Park et al. (2024) extended this line of work by simulating responses from 1,052 individuals in a social science survey, achieving an accuracy rate of 85%.
Similarly, Lu et al. (2025) explored the use of LLM Agents to simulate virtual customers’ shopping behaviors on e-commerce platforms.

LLM Agents have also been applied to study user attitudes toward privacy. For instance, Zhang et al. (2025a); Chen et al. (2024) examined how agents with customizable personas can generate realistic search histories and profile behaviors to explore privacy concerns. In accessibility research, Taeb et al. (2024) proposed AXNav, which uses LLMs to convert manual test instructions into replayable navigation videos for evaluating interface accessibility.
These emerging applications inform our approach: we aim to simulate realistic user behavior in web environments for usability testing, leveraging LLM Agents with diverse, persona-driven characteristics.

Recent advances in LLM-based Web Agents have significantly enhanced the ability of LLMs to assist with web-based tasks.
Early work like WebGPT (Nakano et al., 2022) enabled GPT models to interact with search engines, improving question-answering performance. Subsequent systems, including WebVoyager (He et al., 2024), LASER (Ma et al., 2024), and WebAgent (Gur et al., 2023), extended LLM capabilities to multimodal interaction, complex state space navigation, and long-horizon planning. Claude’s Computer-use API33
3

https://www.anthropic.com/news/3-5-models-and-computer-use further demonstrated precise, general-purpose control over user interfaces beyond web browsers.

Building on top of these advances, researchers have begun to explore the simulation of human online behavior. Lu et al. (2025) proposed a fine-tuning method to enhance model accuracy in predicting the next human action. OPERA (Wang et al., 2025a) introduced a dataset of user online shopping behavior and benchmarked existing LLMs. Inspired by recent advancements in reasoning-enabled LLMs, Shop-R1 (Zhang et al., 2025b) explored enhancing performance through RL. Still, existing work in the NLP field largely focuses on accuracy rather than mimicking human thinking processes. Since these approaches cannot capture qualitative aspects of user decision-making, key challenges in usability testing remain unresolved.

### 2.3. Reasoning Architecture of LLM Agents

Human cognition is often described as operating through two distinct systems: System 1 and System 2 (Kahneman, 2011).
System 1 governs fast, intuitive, emotional, and automatic responses, allowing humans to react quickly with minimal effort.
In contrast, System 2 is responsible for slower, more deliberate processes: it involves conscious reasoning, logical analysis, and problem-solving (Kahneman, 2011; Evans and Stanovich, 2013).
Inspired by this dual-process theory, researchers have explored a variety of reasoning architectures in LLM Agent systems to balance speed and depth of thought.

For real-time responsiveness, many systems use System 1-style reasoning with single-prompt agents like OpenAI Operator44
4

https://openai.com/index/introducing-operator/ and Claude’s Computer-use API55
5

https://www.anthropic.com/news/3-5-models-and-computer-use, which act on immediate inputs without deeper reflection. However, such agents often fail on complex tasks; for example, Lu et al. (2025) found System 1 alone insufficient for simulating realistic user behavior. To improve reasoning, researchers have introduced System 2-style approaches, such as chain-of-thought (Wei et al., 2023), ReAct (Yao et al., 2023), and reinforcement learning–based fine-tuning (DeepSeek-AI et al., 2025).
These models excel in complex domains like programming and solving olympiad-level math problems (DeepSeek-AI et al., 2025; Sun et al., 2025), but their high computational cost and latency (Zhou et al., 2024a; Hua et al., 2024) limit their usability in real-time applications like interactive usability testing.

More recently, researchers have sought to integrate the strengths of both systems into unified reasoning architectures that can support real-time applications while preserving in-depth reasoning.
For instance, Christakopoulou et al. (2024) introduced a talker-reasoner framework for a sleep coaching agent, simulating the interplay between fast reactions and deeper reflections.
Similarly, Zhang et al. (2025c) proposed DPT-Agent, which combines System 1 and System 2 thinking for efficient, simultaneous human-AI collaboration in game settings.
In particular, DPT-Agent uses System 2 to generate high-level instructions, while System 1 is used to translate those instructions into executable policy code for a finite-state machine.
However, extending this approach to the usability study scenario with web environments poses new challenges.
Unlike structured game environments, web environments are dynamic and unpredictable – each click can drastically change the context.
Agents need to continuously adapt their plans in response to newly observed content.
Building on these insights, we propose a two-loop architecture that combines fast, low-latency responses with reflective, high-level reasoning to simulate realistic, goal-directed user behavior in real-world web environments.

## 3. UXAgent: LLM-Agent-Based System for Usability Testing

In this project, we propose UXAgent, a system that can generate LLM Agents as usability testing participants at scale and run simulated interactions with a given web environment to collect simulated user behavioral data.
The architecture of the UXAgent is illustrated in Figure 1. Our system comprises four key components.
The Persona Generator Module generates a large-scale set of diverse personas, which are fed into the LLM Agent.
The LLM Agent Module interacts with a web browser through the Universal Browser Connector Module.
The Universal Browser Connector Module parses the raw HTML as observation and robustly executes agent actions on the web page.
The Result Viewer allows the UX researcher users to easily review and analyze the generated qualitative (e.g., agents’ post-study surveys) and quantitative data (e.g., agents’ interaction logs), or even interview agents directly.

### 3.1. Persona Generator

To support large-scale simulations with users from diverse backgrounds, our system features a Persona Generator module that automatically creates a wide range of agent personas. As an example, generating 1,000 personas takes about two mins.
Users begin by specifying an example persona (e.g., mid-career professional marketing manager; a full example can be found in Appendix D.1) and a target demographic distribution (e.g. 10% low-income, etc.).

The system uses the input example persona as a seed to generate the desired number of agent personas. It first samples demographic attributes based on the specified distribution and then builds full personas using those attributes. To enhance diversity, the system randomly selects one of the previously generated personas to serve as the example in the LLM prompt for generating each new persona.
This prevents repetitive outputs, encourages variation in traits and backgrounds across the generated personas, and allows the system to efficiently generate a rich, demographically balanced set of personas.
The prompts used for persona generation are detailed in Appendix C.1.

### 3.2. LLM Agent Architecture for Usability Testing

#### 3.2.1. Reasoning and Planning Architecture

Inspired by the Dual Process Theory (Kahneman, 2011; Evans and Stanovich, 2013), we designed the LLM Agent with a two-loop structure comprising a Fast Loop and a Slow Loop (Figure 2).
The Fast Loop enables rapid interactions with minimal latency, allowing the agent to promptly respond to changes in the web environment and support real-time simulation.
In contrast, the Slow Loop performs in-depth reasoning, generating high-level insights and strategic guidance to ensure that the agent’s behavior aligns with its intent and persona.
Each loop consists of modules that retrieve memory pieces from the Memory Stream (Section ) and generate memory pieces to be stored in the Memory Stream.
The Perception Module produces observations, the Planning Module generates plans, the Action Module records actions, and the Wondering and Reflection Modules create thoughts.

The Fast Loop and Slow Loop operate in parallel, and share information via the Memory Stream.
For example, high-level reflections generated by the Slow Loop can influence subsequent planning and actions in the Fast Loop.
This non-blocking, asynchronous architecture allows the agent to reason deeply while still maintaining responsiveness, making it well-suited for real-time simulations in complex web environments.

##### Perception Module

To allow the agent to observe and comprehend the outside environment, we designed the Perception Module.
The Perception Module observes the web environment and generates a series of memories describing the LLM Agent’s observations.
Unlike simulated environments, our system interacts with real web pages, and the perception process is designed to mimic how a real human user might visually comprehend a web page.
As shown in Figure 3, the module systematically reads the web page from top to bottom.
The web page is then transformed into a text-form observation memory piece and stored in the Memory Stream.
These observation memories in the Memory Stream are then retrieved and used by other modules to inform subsequent planning, reasoning, and action.

##### Planning Module

To enable real-time decision-making, we designed the Planning Module to mimic human System 1–style rapid cognition by leveraging memory pieces generated by other modules.
This module continuously creates and updates short-term plans aligned with the agent’s intent and persona, based on relevant memories (such as observations and reflections) retrieved from the Memory Stream.
By relying on precomputed insights rather than performing explicit multi-step reasoning during execution, the Planning Module allows the agent to remain responsive while still benefiting from deeper, strategic thinking in the background.

The module mirrors human planning processes by breaking down tasks into logical, interpretable steps. For example, if the agent’s initial intent is to “buy a sofa,” its plan may involve steps such as searching for sofas, applying filters for delivery date and price, comparing product details, and proceeding to purchase.
These plans are continuously refined as new information becomes available through perception and memory updates.
The generated plan is then stored as a plan memory piece in the Memory Stream, to be retrieved and used by other modules.

Specifically, the module performs three core functions:

• 

Initial Plan Creation: At initialization, the agent formulates an initial plan based on the persona’s intent. For example, if the intent is “buy a sofa,” the initial plan may involve searching online stores, reviewing search results, and selecting potential products.

• 

Plan Updates: As new observations and memories emerge, the module updates the plan accordingly. For instance, if the agent is browsing search results and finds a sofa that matches the persona’s preferences (e.g., color or size), the plan evolves to include reviewing detailed information and considering a purchase.

• 

Rationale and Next Step: To ensure transparency and interpretability, the module provides a clear rationale for its current decisions and explicitly identifies the next step required to achieve the agent’s intent, ensuring logical progression toward goals.

##### Action Module

The Action Module is responsible for executing the agent’s planned actions in the web environment. It is designed to mimic how humans translate intentions into interface-level interactions. The module takes as input the current environment state, the agent’s persona and intent, the plan generated by the Planning Module, and relevant memories retrieved from the Memory Stream.

From the current step in the plan (e.g., “I’m going to search for massage lotion”), the Action Module generates a corresponding low-level action defined in the predefined action space (see Section 3.3.2) as well as it’s textual description.
The generated action is executed using the Web Browser Connector and also stored in the Memory Stream as an action memory piece.

##### Importance

The importance score measures how closely a memory piece aligns with the agent’s original intent. In real-world web environments, users often ignore irrelevant elements like ads or unrelated content. To mimic this behavior and improve simulation efficiency, each memory piece is assigned an importance score by an LLM, helping the agent prioritize task-relevant information (e.g., product listings, prices) over peripheral details. To maintain responsiveness, importance scores are computed only in the Slow Loop; memory pieces without a score are left undefined, and their importance scores are ignored during retrieval.

##### Relevance

The relevance score reflects the semantic similarity between a memory and the current context. Each memory’s natural-language description is transformed into a vector embedding, and its cosine similarity is calculated against a query string generated by the retrieval module.

The recency score prioritizes recently created memory pieces, as they are more likely to be relevant to the agent’s immediate task. #### 3.2.2. LLM Agent Generated UX Study Data Traces

To enable UX researchers to analyze both what the agent did and why — thus supporting comprehensive evaluations of web interfaces from multiple perspectives — UXAgent generates a rich set of behavioral and cognitive data from the LLM agent to interact with the web environments via a multi-turn interaction simulation.

This data provides both quantitative and qualitative insights into the agent’s interaction with the web environment (Figure 1). Specifically, it includes:

Action Trace. The system records every action generated by the Action Module in sequence. This trace captures how the agent navigates and manipulates the web interface, including clicks, form submissions, and navigations. It reflects the observable behavior of the agent and can be used for replay, analysis, or visualization of its interaction flow.

Reasoning Trace. In addition to observable actions, the system captures the agent’s internal reasoning trace, including all memory entries generated by the modules within the Reasoning Architecture. This includes observations, plans, rationales, reflections, and wonders. These memories
mimic human participants’ “think-aloud” sessions, provide a window into the agent’s decision-making process, and can be used to gather qualitative feedback from the agent.

Post-Study Survey. After completing their interaction, agents are asked to answer a pre-defined post-study survey. Loaded with their reasoning trace, they respond as if they were human participants, offering feedback on the system and their experience.

### 3.3. Universal Web Connector

We design a Universal Web Connector that enables LLM agents to interact with any real-world web environments. It provides a structured observation space derived from the browser’s DOM through our DOM parser, and robustly executes actions on the page. The interfaces are human-aligned: the observation space reflects how users perceive a web page, and the action space mirrors how users interact with it. Because the connector requires no per-site configuration, UX researchers can easily test new web designs without additional setup.

#### 3.3.1. Observation Space

The observation space of the Universal Web Connector is structured as a JSON object containing:

• 

html: Simplified HTML representation of the webpage.

• 

clickable_elements: List of clickable elements (e.g., buttons, links).

• 

input_elements: List of input elements (e.g., text fields, dropdowns).

• 

hoverable_elements: List of hoverable elements (e.g., hover-triggered menus, tooltips)

• 

select_elements: List of drop-down single select forms

• 

tabs: List of currently available browser tabs

• 

error: Description of errors encountered, such as interacting with a non-existent element.

To mimic human perception of a web page, we design a DOM (Document Object Model) parser that reduces the page to elements visible and meaningful to users. Invisible content such as scripts, styles, and metadata is discarded, along with elements hidden by CSS, rendered at zero size, or pushed entirely off-screen. To reduce structural redundancy, the parser collapses trivial nesting of non-semantic containers, such as chains of <div> wrappers, and prunes empty elements. Exceptions are made for controls that may legitimately appear empty (e.g., <input>, <img>, etc.).

The parser heuristically determines whether elements are interactive. Nodes are marked as clickable if they are native controls (e.g., <button>, <input>), anchors with href, elements with explicit onclick handlers, or elements with ARIA roles such as button or link. Humans can easily distinguish between selectable text (indicated by “”) and clickable elements (indicated by “”), whereas agents often attempt to click on plain text or other non-interactive elements. To reduce such errors, we expose the same cues available to humans: elements with a computed cursor style of pointer are considered clickable. To further identify hover-sensitive targets, we monkey-patch addEventListener so that whenever a node registers a hover event listener, it is annotated with maybe-hoverable=true.

To enable the model to reference elements during actions, each interactive element is assigned a stable, human-readable identifier derived from visible text, placeholders, or tag names. Identifiers are normalized to short slugs, scoped hierarchically, and made unique with numeric suffixes. Both the stripped node and original DOM share the same semantic-id, with clickable elements additionally marked clickable=true. Additionally, since JavaScript states such as input values are not directly available in the HTML, the parser extracts and records them, including values, selections, and focus, and assigns semantic identifiers where needed.

Optionally, when the user wants to evaluate layout-level features, such as comparing two different designs, the observation space can also include a full-page screenshot of the webpage. This provides access to visual cues such as spatial arrangement, alignment, and whitespace that are not recoverable from the stripped DOM alone. By default, the system uses text-only observations, which are more compact and faster to process, while the visual extension offers richer context at the cost of additional computation.

#### 3.3.2. Action Space

We design the action space so that agents can perform the same primitive interactions as human users (click, type, hover, select, navigate, manage tabs). To reduce latency and eliminate unnecessary branching, we explicitly remove the scroll action (the environment automatically scrolls the target element into view before execution). Targets are referenced by the stable semantic identifiers described in the observation construction (semantic-id), which makes actions robust to minor DOM changes. After each action, the executor waits for network and UI quiescence (for example, no active requests for a short idle window) before returning the next observation. This design addresses prior challenges of noisy action choices, arbitrary code generation, and nondeterministic post-action states by keeping the action set compact, interpretable, and synchronized with the rendered page.

All actions that operate on elements identify their targets using semantic IDs that are guaranteed to be unique within the current observation. Before execution, the environment validates that the target remains interactable, scrolls it into view automatically (therefore, no explicit scroll action is necessary), performs the operation, and then waits for an idle period before emitting the next observation. ## 4. Case Study: A Usability Testing Simulation with UXAgent to Evaluate a Newly Designed Product Filter Feature in an Online Shopping Website

We chose online shopping, a common and highly personalized use case, to illustrate how UX researchers can use UXAgent to augment their usability testing work practice.
In our evaluation study, we used WebArena (Zhou et al., 2024b) as our target online shopping web environment.
We chose WebArena as our experiment platform because it works similarly to Amazon.com and is a publicly available online shopping environment, widely used in many web agent studies(Su et al., 2024; Yang et al., 2024).

### 4.1. LLM Agent’s Usability Testing Task and Simulated Participant Data

In our study, we first created an initial usability testing study protocol borrowed from prior HCI works (Moser et al., 2017; Prakash et al., 2024).
We employed the Persona Generator Module to create 20 agent personas, ensuring a uniform distribution across gender (male, female, and non-binary) and online shopping frequency (a few times per year, a few times per month, and a few times per week).
LLM agent module uses each persona to perform a usability testing task: “Buy a mean substitute. With the highest rating and within a budget between $100 and $200. You don’t need to finish the purchase, just go to the checkout page.”
LLM agents were free to explore the WebArena shopping environment via multi-turn interaction to test the newly designed feature of “product filtering panel” (Zhou et al., 2024b).
They may or maynot use the filter naturally, or they could either complete a purchase or terminate the session without purchase, if they could not find a suitable item.
During each session, our system recorded the full simulation result, including the LLM agent participants’ reasoning and action traces, as well as their post-study surveys.
Examples of the generated data are shown in appendix D.
As a reference to the system’s scalability, running 20 simulations took approximately 90 minutes, and 1,000 simulations took about 12 hours.
The overall runtime primarily depends on the LLM API’s rate limits or token throughput.

### 4.2. User Study with 16 UX Researchers

We recruited 16 UX researchers to participate in a heuristic evaluation study with reviewing the 20 simulated sessions using UXAgent.
The detailed demographics and experience levels of these UX researcher participants are summarized in Table 1. Five participants reported more than 5 years of UX research experience, two reported 4–5 years, three reported 3–4 years, one reported 2–3 years, five reported 1–2 years, and one reported less than one year. Most participants rated themselves as 3 within 1 to 5 in usability testing familiarity (M=3.87, SD=0.92).

Each study session lasted approximately 30 minutes and was video recorded if they consented. Participants were first presented with the initial draft of the usability testing study design protocol (included in Appendix B); if they are unsatisfied, they are instructed to make suggestions to revise the study design.
They then used the Study Configure Interface to config the study design in UXAgent.
To accommodate the time limit, participants were provided with results from a pre-configured run rather than executing new simulations within the 30 mins of study sessoin in real-time.
Using the Result Viewer Interface, they reviewed and analyzed the generated data of the 20 LLM agent participants.
UX researcher participants also conducted a post-study interview with the LLM agent, following the interview protocol defined in the draft study design.

After completing the data analysis and interviewing the agent, UX researchers were asked to propose improvement suggestions both to the initial study protocol and to the new “filter feature” design on the shopping website.
Finally, they completed a post-study survey consisting of Likert-scale items evaluating UXAgent’s ease of use, the helpfulness and trustworthiness of the generated data, and their satisfaction with the revised protocol.
We also administered a structured questionnaire, which included items probing how participants think “LLM agents could replace human participants in the future usability testings”, as well as open-ended questions to gather their feedback on UXAgent’s desired new features, additional data modalities, potential risks, and other qualitative feedback. A photo of one user study session is shown in Fig. 9.

##### UX researcher participants went through a four-step paradigm of using UXAgent:

1) Building trust with data, 2) sense making of the data, 3) proposing hypotheses and in-depth exploration, and 4) drawing conclusions.

When participants had access to all types of data generated by UXAgent, their predominant response was to examine each data type to ensure its trustworthiness.
Most participants only proceeded with deeper analysis after confirming the data’s trustworthiness. However, some participants began to analyze the data early on without fully verifying their trustworthiness and encountered challenges at later stages.
Once trust was established, they moved on to the sense-making phase, where they tried to interpret the data and understand the relationships between different variables.
P3 used the sorting feature to understand different agents’ behavior and picked the agent that made the most clicks on the filters to interview to understand why.
Participants then made hypotheses on the experiment result and made detailed observations to verify their hypotheses.
Most participants noticed agents were looking to sort products by their reviews, but couldn’t find the system feature.
They then checked the raw action log and interviewed the agent about their feelings about this.
Participants then discussed what they found during the analysis of the simulated result.
They organized the findings and discussed how they were going to revise and iterate their study design after the simulation.

##### UX Researchers can use the UXAgent to gather early feedback from LLM agents and iterate the study design.

Before the study, 12 of the 16 participants suggested minor revisions to the initial usability testing protocol, while the remaining participants agreed that the original design was ready for a human pilot study.
The proposed changes included adding additional measurements, increasing the number of participants, and, in some cases, modifying the system’s UI design.
Afterward, all 16 participants were satisfied with the revised study protocol and proceeded to use UXAgent.
During each session, the UX researcher participants followed our study protocol, as described in Sec. 4.2, to review the LLM agent–simulated usability testing data, conduct interviews, and perform analyses.
At the end of the session, each participant also completed a post-study questionnaire with open-ended questions to report their perceived trustworthiness and satisfaction with UXAgent.

The result shows that although all of them were satisfied with their initial study protocol, almost all participants (14 out of 16) proposed additional improvements to the study design with the help of the UXAgent.
Of the 14 participants who proposed additional improvements to the study design, 6 suggested changes to the participant tasks (P1, P2, P3, P4, P6, P14), such as adding additional filtering tasks, or ensuring task alignment with study goals.
Three participants recommended recruiting from different or more diverse demographic groups (P5, P10, P12) to avoid bias and better capture varied perspectives:

[P5]
…add restrictions on the highest level of degree of participants since all of them seem to be bachelor’s graduates. This might cause some bias to the study.

Two participants proposed adding or refining survey questions (P7, P11, P15), and another two suggested expanding or improving the interview protocol to capture more comprehensive user experiences (P7, P8).
Additionally, two participants recommended incorporating more metrics or measurements into the study design (P13, P14).
These results show that UXAgent can effectively support early feedback collection for iterating on study designs.

##### UXAgent supports UX researchers to come up with new design ideas of system features

Regarding the to-be-evaluated feature design of the system, participants also made use of the simulated data generated by UXAgent.
For example, seven participants explicitly suggested adding or refining a rating-based sorting or filtering mechanism (P2, P3, P5, P6, P7, P10, P11).
Others proposed additional enhancements such as customizable price filters (P2, P5) and more detailed product tags (P2).

[P2]
Add sort and filter by rating, price buckets. improve category results.

Several participants also recommended improvements to the usability and flexibility of the filter panel, including multi-select options, better category design, and enhanced ranking and relevance (P12, P13, P14, P16).

[P16]
Include badges/markers specific to the item being purchased in the filters. For example, for clothings, maybe the brand, the use (e.g., casual), and the colors.

Finally, two participants pointed out interface issues with the filter panel and recommended making it sticky to remain visible during navigation (P4, P9), while another suggested improving its visual prominence (P14).
These findings suggest that UXAgent can effectively support UX researchers to come up with new design ideas for the system feature, which serves the ultimate goal of the usability testing method.

## 5. Discussion

### 5.1. Design Considerations for LLM Agent Systems in User Study

The shift towards using LLMs to assist UX research has demonstrated considerable potential. With UXAgent, we show that LLM agents can support user studies by enabling faster design iterations through user behavior simulation, thereby reducing costs and improving the quality of study design (Decker-Maurer, 2012). Building on these findings, we outline several design considerations to guide the development of future systems involving AI-simulated agents in user studies.

##### Generate high-level insights from raw data.

Future systems should help researchers move beyond raw reasoning traces by automatically generating high-level insights. As P5 noted, visualizations beyond simple aggregate measures (e.g., mean values) would make it easier to intuitively identify issues. Similarly, P3 reported feeling overwhelmed by the detail page, suggesting that concise summaries of memory data would improve usability.

##### Support more modalities of simulation and result.

Future systems should extend beyond text-based interaction and static outputs (Liu et al., 2025; Kuang et al., 2023). P3 suggested enabling LLM agents to interact with systems through voice and tone, thereby broadening applicability to domains such as conversational interfaces. P4 recommended incorporating video replays in addition to step-by-step traces to better capture the dynamics of interactions. P2 further emphasized the need to expand beyond web environments to include graphical user interfaces. Together, these suggestions highlight the importance of supporting multimodal simulation and diverse result formats to improve both ecological validity and researcher insight.

### 5.2. Potential Downstream Application for LLM Agent Systems

In this work, we explored the use of LLM Agents to simulate human participants in the context of usability testing. However, the underlying capabilities of these agents—such as reasoning, goal-driven behavior, and interaction with web environments—open the door to a variety of downstream applications beyond UX research.

##### Help with Low-Resource UX Research

Although LLM agent simulations cannot yet replace human participants, they can be a valuable resource in low-resource research settings. In many educational contexts, students conducting usability studies often rely on friends or family members as participants due to limited access to target users (Houde et al., 2025; Wang et al., 2025b). A system like UXAgent could help by providing simulated participants that approximate realistic user behaviors, allowing students to practice study design, iterate on protocols, and identify usability issues before recruiting actual participants. Similarly, independent researchers or practitioners with limited budgets could use simulated agents to pilot studies quickly and cost-effectively, reducing reliance on extensive recruitment and compensation (Kapania et al., 2025). While these simulations are not substitutes for human data (Ashkinaze et al., 2025), they can significantly lower the barrier to entry for conducting UX research and provide a practical first step in the iterative design process.

##### Digital Twin for End-User Task Automation

LLM Agents can serve as “digital twins”, acting on behalf of users to complete tasks in web environments (Vahdati et al., 2025). For example, in online shopping scenarios, a future system could allow users to specify their preferences and intents (e.g., budget, brand, or product features), and delegate the search, comparison, and purchase decisions to a personalized agent. This application would enable users to offload routine decision-making while still aligning outcomes with their goals.

##### Evaluation of Existing AI Systems

Simulated users can also serve as proxies for evaluating existing AI systems, such as recommender systems and search engines (Ma et al., 2025; Zhao et al., 2025). Unlike traditional evaluation methods that rely on historical interaction logs or static benchmarks, LLM Agents can dynamically engage with system outputs, simulate realistic user behavior, and provide feedback. By assigning diverse personas to the agents, researchers can examine how users with different goals, preferences, or constraints interact with AI systems. This simulation-based approach offers a richer, more nuanced perspective on system performance, fairness, and user alignment across varied use cases.

##### Simulating A/B Testing with Behavioral Feedback

LLM Agents can be deployed to simulate A/B tests for different interfaces and model variants, not only measuring which version performs better in terms of task success but also collecting rich behavioral data and simulated feedback.
This enables researchers to evaluate both the quantitative and qualitative impact of design changes before allocating real A/B testing resources, potentially reducing iteration cycles and development costs.

### 5.3. Resolving Risk and Privacy Concerns

While LLM-assisted UX study systems offer substantial benefits for user studies, they also introduce significant risks and concerns, particularly around privacy and ethical use (Li et al., 2024a; Shao et al., 2024).
A notable concern about sensitive data might arise in applying LLM Agents in user studies in fields such as healthcare (Peris et al., 2023).
Our participants viewed data from LLM Agents as supplementary rather than definitive, which is consistent with prior findings that LLMs cannot fully replace human subjects in psychological experiments (Cui et al., 2024).
This preference reflects their ability to detect biases, limiting acceptance of LLMs as accurate representations of outcomes (Schmidt et al., 2024).

Another critical issue is the risk of researchers misusing AI-generated data (Peris et al., 2023).
Some may be tempted to use this simulated data as a substitute for actual human participant data, potentially bypassing real user studies altogether.
This could lead to flawed conclusions, as the AI-generated data, while useful for simulations, cannot fully replicate the complexity of real human behavior.
We believe that addressing these risks requires a clear understanding of the limitations of LLM-generated data and establishing rigorous ethical guidelines and robust privacy safeguards to ensure responsible and effective integration of LLM in UX research.

### 5.4. Limitations and Future Works

There are several limitations in our work.
First, the limited number of participants in our heuristic evaluation may not fully capture the diversity of user experiences or the generalizability of the findings.
A larger scale of rigorous user testing in the future will help us further explore the effectiveness of UXAgent.
Also, our current work focuses only on the qualitative analysis of the participants’ perspectives toward LLM Agent simulation, but not on quantitative evaluations of the LLM Agents’ versus real humans’ shopping behaviors.
It is crucial to conduct a systematic analysis comparing LLM-generated simulations with real human participants in order to further understand how UX researchers could benefit from using such agents.

Our current results confirm the effectiveness of UXAgent in web-related user research, as well as the potential of LLMs in simulating user behavior to assist rapid iteration of user research.
In the future, this work could be expanded to encompass a broader range of user research contexts beyond web applications.
This might include adaptation to UI/UX design in desktop, mobile, or mixed-reality environments, where LLM Agents could simulate user interactions in complex, multi-modal interfaces.
Also, we only tested giving the agents an explicit intention of “buy a jacket”. Experimenting with other intents, such as window shopping, can also help understand the ability and limits of LLM Agent.
Additionally, the action space of the agent is currently limited to basic actions such as “click” and “type”. Supporting other types of actions, such as “wait”, “read”, and “scroll” can allow the experimenter to collect more information useful to their study.

## 6. Conclusion

In this work, we present UXAgent to support researchers in conducting simulated user studies.
By providing action traces, reasoning traces, and post-study survey results, the system supports iterative refinement of both UX study designs and feature designs.
Our case study with 16 UX researcher participants suggests that UXAgent helps them identify potential flaws in study protocol and gains early insights into how users might perceive and interact with the proposed web feature, thus improving the quality and reducing risks of the later experiments with real human participants.
Our study is the first step towards a promising future of UX researchers to use LLM agents to achieve “human-AI collaboration” in the field of UX research.

How I use my memories

1. Retrieve: I identify memories whose content semantically matches the

question’s topic.

2. Rank: I sort them by recency (timestamp descending), then by

specificity.

3. Resolve conflicts:

- If my memories disagree, I choose the most recent credible one.

- If still tied, I choose the most specific one.

4. Answer every question:

- For multiple_choice: I select the closest option. If no direct

match, I use "Other" if available.

- For text: I paraphrase concisely from my memory.

5. Be literal but holistic: I infer answers from my overall memory

context, not individual IDs.

Answering rules by type

- multiple_choice:

- value must be one of the provided options.

- short_text / long_text:

- I prefer concise paraphrase; max ~160 chars.

- If nothing relevant exists, I use "N/A".

Output schema (I MUST follow this exactly)

I return a single JSON object:

{

"questionnaire_id": "string",

"answers": [

{

"question_id": "string",

"value": "string | number | boolean",

"reason": "verbose rationale showing memory context -> reasoning -> answer"

}

],

"meta": {

"confidence_overall": 0.0

}

}

Field requirements

- answers: one entry per question in the questionnaire (preserve

order).

- value:

- If type = multiple_choice: must be exactly one of the provided

options.

- If type = text: a string (or "N/A").

- reason: one verbose explanation (memory context -> reasoning ->

answer).

- meta.confidence_overall: float in [0,1], reflecting my aggregate

certainty.

Validation & safety checks

- I ensure every question has an answers entry.

- For multiple_choice, I confirm value is in options.

- No fields outside the schema. No prose outside JSON.
